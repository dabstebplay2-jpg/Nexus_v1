## Исправленные проблемы

1. `Format-List` больше не совпадает с опасной командой `format`. Приведённый пользователем pipeline классифицируется как READ и выполняется без запроса разрешения. Автоматическое разрешение shell ограничено буквальными командами перечисления и форматирования; выражения, произвольные пути и перенаправления не входят в этот список. Для чтения содержимого предпочтителен защищённый инструмент read.
2. Одиночное удаление требует подтверждения DELETE. Явный deny остаётся приоритетнее подтверждения. Рекурсивные опасные операции и системные настройки сохраняют SYSTEM_MUTATION с запретом по умолчанию. Составные команды собирают несколько capabilities, вместо возврата по первому совпадению.
3. Модель получает Windows PowerShell как фактическую оболочку, пример Get-ChildItem и рекомендации по путям. Имя инструмента bash сохранено для совместимости.
4. PowerShell разбирает команду собственным AST-парсером. Проверки после команд обнаруживают промежуточные ошибки и ненулевые коды внешних программ, включая pipeline и вложенные блоки. Сохраняется передача объектов по pipeline. Служебный progress XML подавлен; вывод настроен на UTF-8.
5. Отказ разрешений содержит инструмент, аргументы, capabilities, причину и способ продолжения. Неуспешная shell-операция содержит отдельные потоки, общий exit code и объяснение; исходный код внешней программы указан в диагностике.

## Добавленные тесты

- Классификация READ / WRITE_PROJECT / DELETE / SYSTEM_MUTATION, смешанные команды, опасные рекурсивные операции и исключение выражений из автоматического разрешения.
- Принятие и отклонение подтверждения удаления; приоритет явного deny.
- Сохранение FAILED, stdout, stderr и диагностики в реальном ledger/evidence.
- Выбор оболочки и наличие Windows-инструкций в контексте модели.
- Реальные ошибки cmdlet, native command, нескольких native commands, pipeline и вложенного блока; строка с точкой с запятой; Unicode; допустимое предупреждение в stderr; сохранение содержимого и фильтрации pipeline.
- A: list → read → реальное перечисление PowerShell, без permission error. Для завершения используется доверенная проверка наличия изучаемых файлов: существующий coding contract требует доказательства цели.
- B: read → edit → verify, с реальным исправлением файла и запуском проверки результата.
- C: удаление переводит задачу в WAITING_PERMISSION; файл остаётся на месте.
- D: системная настройка отмечена высоким риском и заблокирована до выполнения с понятной причиной.

Провайдер модели в сценариях детерминированный. Файлы, SQLite, shell и проверки настоящие; эти тесты проверяют поведение агента, но не качество генерации команд конкретной LLM.

## Риски для этапа нового UI

Блокирующих проблем совместимости по выполненным проверкам не обнаружено. Новому UI нужно отображать WAITING_PERMISSION, action.error и отдельные stdout/stderr из metadata; общий output остаётся доступен.

Shell остаётся неограниченным исполнителем, а классификация опасных команд — консервативной эвристикой, не OS sandbox. Не следует глобально разрешать RUN_PROCESS для недоверенных команд. Неизвестные формы команд по умолчанию требуют подтверждения.

Адаптер намеренно останавливается на ошибках. Скрипты, рассчитывающие на продолжение после сбоя, следует разбивать на отдельные вызовы. Внешняя программа или отдельно запущенный скрипт, скрывающие собственную ошибку за exit 0, остаются вне наблюдения родительской оболочки; COMMAND_RESULT не заменяет trusted verification.

На Unix адаптер использует Bash с errexit/pipefail, поэтому требуется установленный Bash. Его аргументы покрыты тестом, но реальные Unix-процессы в этом Windows-прогоне не запускались. Перед Unix-релизом нужен отдельный прогон на целевой системе.
