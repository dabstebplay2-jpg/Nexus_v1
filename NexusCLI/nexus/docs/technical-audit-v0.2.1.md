# Технический аудит Nexus v0.2.1

Дата: 10 сентября 2026. Проверена рабочая версия после стабилизации. Аудит основан на коде, regression-тестах, реальных Windows-процессах, SQLite и HTTP/SSE smoke-проверках. Реальные модели и облачные API в этом аудите не опрашивались: модель заменена детерминированным провайдером.

## Вывод

Существующую архитектуру можно использовать для следующего этапа разработки продукта. Переписывать Agent Loop не требуется. Однако готовность к разработке нового UI не равна готовности публичного релиза: остаются вопросы контрактов для исследовательских задач, бюджетов продолжения, устойчивого replay событий и безопасного rollback.

UI и дизайн не изменены. В Core внесена только проверка уже завершённой задачи перед повторным обращением к модели. Остальные исправления находятся в существующих tools, recovery, permissions, API и shared-модулях серверных данных.

## Приоритеты и исправления

P1 — до пользовательского релиза; P2 — следующий этап надёжности/масштабирования. Статус «исправлено» относится к перечисленному сценарию, а не к доказательству отсутствия всех ошибок в подсистеме.

## Lifecycle

Дополнительно исправлена P1-проблема ledger: безопасный shell READ сохранялся с высоким риском и sideEffect=true. Его прерывание могло блокировать recovery как неизвестную мутацию. Теперь READ-only capabilities дают низкий риск и sideEffect=false; обработка ошибок использует свойства конкретного action. Операции с записью сохраняют прежнюю защиту.

Фактическая нормальная последовательность: RECOVERING → UNDERSTANDING → PLANNING → ACTING → OBSERVING → VERIFYING → COMPLETED. COMPLETE — значение decision.outcome; COMPLETED — состояние session. Их переименование не требуется.

Reproduction может выполняться до UNDERSTANDING: RECOVERING → VERIFYING → RECOVERING. После отклонения предложения о завершении разрешено RECOVERING → ACTING. Это повторные итерации существующего цикла, а не ошибки переходов. Только CompletionPolicy разрешает переход в COMPLETED.

Не все FAILED означают ошибку выполнения. Сейчас Core использует FAILED и для NEEDS_USER_INPUT, когда отсутствует обязательное доказательство цели. Неопределённые побочные эффекты блокируют продолжение; автоматического replay нет. UNKNOWN результата проверки и UNKNOWN исполнения процесса имеют разные причины и требуют разных действий.

Оставшиеся причины нежелательного FAILED:

- **P1: бюджеты сессии.** turns/toolCount/activeMs сохраняются между run и новыми сообщениями. Время ожидания пользователя также попадает в activeMs. Нужны отдельные лимиты активного исполнения и ожидания, плюс явная политика продления бюджета; безусловный сброс убрал бы защиту от бесконечных циклов.
- **P1: изменение требований после reproduction.** promote увеличивает contract revision, но baseline fingerprint остаётся исходным. Старое baseline evidence может перестать соответствовать новой revision, а заново воспроизвести исходный снимок после правок нельзя. Нужна явная миграция контракта с проверкой неизменности trusted check; простое принятие старого PASS/FAIL небезопасно.
- **P2: неподдерживаемые возможности модели и размеры контекста.** Coding-задача с моделью без tool calling не становится полноценным агентным запуском. Capability admission и проверка бюджета контекста должны происходить до дорогостоящего run.

## Permissions

Проверены guarded list/read/edit/write, неизвестные shell-команды, одиночное и рекурсивное удаление, системные операции, смешанные команды и подтверждение/отказ.

- list/read используют READ; Workspace Guard проверяет границы, секретные пути, junction/symlink, устройства Windows и NTFS streams.
- edit/write используют WRITE_PROJECT и expectedHash; устаревший hash отвергается. Это не блокировка внешнего редактора на всё время операции: гонка между проверкой hash и rename остаётся отдельной P1-задачей перед функцией apply/rollback.
- Буквальный безопасный pipeline Get-ChildItem разрешён как READ. Произвольный Get-Content в shell не получает автоматического доступа к файлам в обход guard.
- Одиночное удаление запрашивает подтверждение DELETE; явный deny имеет приоритет. Опасные рекурсивные и системные операции по умолчанию запрещены.
- RUN_PROCESS — разрешение неограниченного shell, не OS sandbox. Динамические вызовы, скрипты, методы .NET, aliases и процессы с внутренними побочными эффектами нельзя полноценно классифицировать регулярными выражениями. **P1:** для продукта сохранять подтверждение неизвестных команд; не включать глобальное allow RUN_PROCESS. Расширение автоматических разрешений требует структурированного разбора и контроля путей/провайдеров.

PowerShell AST instrumentation проверяет ошибки непосредственно в переданной строке команды. Отдельный дочерний скрипт/программа может скрыть собственную ошибку за exit 0; поэтому shell PASS по-прежнему не является доказательством достижения произвольной цели. Unix-ветка использует Bash/pipefail, но реальные Unix-процессы в этой Windows-среде не проверены.

## Evidence и критерии успеха

Coding-задача доказуема, когда для каждого обязательного критерия есть evidence нужного kind/checkId/source, актуальной contract revision и source fingerprint. План должен быть закрыт; неизвестные побочные эффекты блокируют завершение. Нельзя заменить trusted check текстом модели или произвольным shell PASS.

NEEDS_USER_INPUT возникает закономерно, если проектные checks прошли, но общий goal не имеет своего trusted check или пользовательского подтверждения. Внешне особенно заметен разрыв для «изучи проект»: coding mode требует goal proof, а answer mode вообще не предоставляет инструменты.

**P1: добавить отдельный inspection contract**, не ослабляя coding contract. Его критерии: подтверждённые чтения/список исследованных файлов, ссылки на evidence в ответе, отсутствие записей и явное обозначение результата как исследования, а не исправления. Для repair оставить reproduce → edit → trusted verification. Для feature принимать критерии/goal check при создании задачи. После STEER показывать, какой критерий изменился и какое доказательство теперь нужно.

Дополнительно: DONE в плане подтверждает наличие passing evidence, но не семантическую связь между шагом и этим evidence. **P2:** типизированные критерии плана и привязка к конкретному check/file/action; финальная CompletionPolicy остаётся единственным решением о завершении.

## Память и восстановление

История задач, сообщений, действий, evidence, проверок, событий и context epochs хранится в SQLite. Есть optimistic session version и блокировка workspace/session; существующие тесты покрывают повторное открытие, crash, владение workspace и отсутствие автоматического replay.

ProjectContext строится из project detection; InstructionsContext включает AGENTS.md; Git baseline и текущие evidence/actions подаются в ContextManager. Компактизация сохраняет историю в ledger, но её summary эвристический и не является самостоятельным доказательством.

**P2:** межзадачная память проекта сейчас ограничена настройками и доступной историей. Автоматического безопасного переноса проверенных фактов между задачами нет. Добавлять его следует как ContextSource с происхождением, сроком актуальности и fingerprint; не подмешивать старые ответы модели как инструкции.

**P1 для длинных пользовательских сессий:** RunManager держит последние 5000 событий; cursor и часть событий формируются в памяти. Durable история есть, но текущий replay не гарантирует восстановление произвольного старого cursor после переполнения/перезапуска. Нужны устойчивый sequence из ledger, пагинация и явный ответ о пропуске диапазона. Это серверная задача, не изменение дизайна.

## Подготовка архитектуры к следующим функциям

| Функция              | Основа сейчас                                                                                                     | Безопасный следующий шаг                                                                                                                                                                                                                                    |
| -------------------- | ----------------------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Cursor-подобный diff | FILE_CHANGE, привязка к action, unified patch; добавлены path, beforeHash, afterHash, created, snapshotIntegrity. | Строить diff по данным API; группировать последовательные действия по файлу, отдельно показывать неприписываемые процессам изменения. Проверять текущий afterHash перед apply/revert.                                                                       |
| Несколько моделей    | Provider port и ModelConfig в запросе; одна модель фиксируется в сессии.                                          | Выбор на границе turn с сохранением полного model/provider config и capability snapshot в Turn. Не менять провайдера посреди stream и не повторять tool execution при fallback.                                                                             |
| Локальные модели     | OpenAI-compatible transport, configurable endpoint и capability flags; local-models tests.                        | Перепроверять tool calling, streaming и реальный context length выбранной модели. Наличие пресета не доказывает совместимость конкретной загруженной модели.                                                                                                |
| Другие API providers | Изолированный Provider.stream, унифицированные ModelEvent; адаптер не исполняет tools.                            | Добавлять native transport отдельной реализацией Provider; ошибки, usage, finish reason и tool schema проверять контрактными тестами. UI не должен знать формат провайдера.                                                                                 |
| Rollback             | Хеши записей и проверяемые снимки в diff, guard и conditional edit.                                               | Отдельное подтверждаемое действие: workspace lock → currentHash==afterHash → lossless before snapshot → atomic write/delete → новая запись ledger → повторная verification. Отказ при конфликте, redacted snapshot и неподтверждённых изменениях процессов. |

snapshotIntegrity=verified означает совпадение сохранённых версий с хешами конкретного действия. Это **не** разрешение на rollback, не проверка текущего файла и не гарантия восстановления всего workspace. Git reset --hard для rollback задач использовать нельзя: он затронет пользовательские изменения.

## Файлы этого аудита

- `src/core/agent-loop.ts`: повторная проверка завершённой задачи без нового модельного turn.
- `src/composition.ts`: достоверный aggregate verdict verify и callback ожидания.
- `src/tools/registry.ts`, `src/tools/executor.ts`: передача waiting в ToolContext и согласование риска/побочных эффектов READ с ledger.
- `src/recovery/policy.ts`: восстановление результатов из ledger.
- `src/permissions/engine.ts`: дополнительные ложные срабатывания и строгая обработка опасных вложенных shell-команд.
- `src/api.ts`, `src/git/changes.ts`: дополнительные данные diff и проверка целостности снимков.
- `apps/shared/run-report.ts`: согласованность evidence и рекомендаций с решением Core.
- `apps/shared/projects.ts`: атомарная запись настроек проектов.
- `test/audit.test.ts`: 13 новых regression-тестов.
- `docs/technical-audit-v0.2.1.md`: этот отчёт.

Изменения предыдущей стабилизации сохранены. Версии package.json, схема БД, frontend и HTTP-маршруты не менялись. Поля diff добавлены к существующему ответу; patch сохранён. ToolContext расширен обязательным внутренним callback waiting.

## Проверки

Четыре первоначальных regression-теста сначала воспроизвели дефекты (повторный run, verify FAIL/empty и recovery), затем прошли после исправлений. Дополнительно проверены изменения файлов после completion, новые сообщения, lifecycle, вложенное ожидание permission, ошибка запуска check, stale report, отказ permission, integrity diff и redacted snapshot.

Итоговые проверки прошли:

- `bun run check`: 7/7 — typecheck, boundaries, test, bench, build, smoke, product. Внутри check используется Bun 1.3.14 из проекта.
- `bun test ./test`: 129 passed, 0 failed, 485 assertions, 10 файлов; отдельный прогон на Bun 1.4.2 из PATH. Тот же набор прошёл внутри check.
- `bun run web:build`: TypeScript и production-сборка Vite — PASS.
- `git diff --check`: PASS; форматирование изменённых файлов проверено Prettier.

Всего добавлено 13 тестов аудита; 9 тестов предыдущей стабилизации сохранены. Файловые, permission, recovery и provider regression-проверки не отключались. Проверки моделей используют тестовый провайдер и локальные HTTP fixtures; это не сертификация всех реальных LLM/backend.
