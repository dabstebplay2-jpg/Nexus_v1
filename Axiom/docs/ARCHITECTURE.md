# Архитектура Axiom v0.1-alpha.2

## Решения

Один npm workspace-монорепозиторий, TypeScript strict с `noUncheckedIndexedAccess`. React + Vite выбран вместо Next.js: локальному чату не нужны SSR и SEO, а отдельный API делает связь с будущими Code/CLI явной. Express — транспорт и composition root, а не место бизнес-логики генерации. SQLite из Node 24 исключает компиляцию нативного стороннего модуля при установке на Windows. Это один локальный процесс сервера, без микросервисов.

## Направление зависимостей

```text
Chat UI ── HTTP / NDJSON ──> Server (composition root)
  │                          ├── Core ───────────────┐
  └── shared (types)         ├── Providers ──────────┤
                             └── Storage ────────────┤
                                                    ▼
                                             shared (ports/types)
```

Core **не импортирует** Express, React, SQLite или конкретные адаптеры. Он принимает `ChatRepository`, `ContextBuilder` и `AIProvider`. Сервер создаёт SQLite/SecretStorage, регистрирует фабрики адаптеров, разрешает выбранную модель по конфигурации и передаёт Core. Providers не зависят от UI/Storage; секреты получают через интерфейс `SecretStorage`. UI использует только JSON-контракты и общие типы, без SDK поставщиков и API-ключей при генерации.

Будущий CLI сможет напрямую собрать эти же Core/Providers/Storage или обращаться к HTTP API. Будущий Code сможет добавить новые use cases в Core. UI-библиотека пока не вынесена в отдельный пакет: переиспользуемые компоненты живут в `apps/chat/src/components`, пока нет второго потребителя.

## Доменные модели

`Conversation` — метаданные. `Message` — роль, статус, модель/провайдер, время и массив `MessagePart`. Типы частей: text, image, file, tool-call, tool-result, reasoning metadata. `Attachment` хранит идентификатор и описание файла. В v0.1 текст и data URL изображений хранятся внутри сообщения; отдельное объектное файловое хранилище — v0.2.

`Model` имеет независимые `id` и `provider` (ID подключения), displayName, locality, необязательный contextWindow и расширяемый словарь capabilities. Ключ избранного — сериализованная пара `[provider,id]`, поэтому одинаковые имена моделей разных серверов не конфликтуют. `true` — поддерживается, `false` — нет, отсутствие — неизвестно. У обнаруженных моделей не угадываем reasoning/tools/vision по имени.

## Генерация

1. API проверяет запрос Zod-схемой и разрешает модель из сохранённого подключения.
2. Core проверяет диалог, возможности и блокировку активного ответа.
3. ContextBuilder формирует бюджетированный запрос из предполагаемой истории: complete и непустые aborted assistant, без error/generating. System-инструкции закрепляются; старые целые ходы исключаются из запроса. Слишком большой последний ход вызывает ошибку до записи.
4. В транзакции сохраняются пользовательское сообщение и пустой assistant со статусом generating. Первый заголовок берётся из первых 64 символов пользовательского текста без LLM.
5. Провайдер возвращает `AsyncIterable<ProviderEvent>`. Core переводит его в `ChatEvent`; API выдаёт NDJSON. UI обновляет текст по мере прихода delta.
6. Частичный текст сохраняется каждые ~300 мс и обязательно в `finally`. Отмена, ошибка и нормальное завершение имеют отдельные статусы.

`AIProvider.chat()` существует для непотоковых потребителей; базовый `StreamingProvider` собирает результат из того же потока. OpenAI-compatible разбирает SSE внутри адаптера — транспорт поставщика не проникает в Core/Chat.

## Отмена и согласованность

На диалог хранится один AbortController. Повторная одновременная генерация отклоняется до записи. Stop API, закрытие HTTP-потока и завершение процесса отменяют запрос. Mock ждёт отменяемые таймеры, HTTP-провайдер передаёт signal в fetch. Core снимает блокировку и сохраняет финальный статус в `finally`. При старте SQLite переводит оставшиеся generating в aborted. При аварийном завершении можно потерять не более последнего несохранённого фрагмента; автоматического возобновления генерации нет.

Редактирование удаляет редактируемое сообщение и всё после него, затем пишет новое. Regenerate сохраняет последнее пользовательское сообщение и заменяет ответ. Это линейная история; ветвление предусмотрено отдельной будущей миграцией. Удаление диалога с активным ответом запрещено.

## Хранилище

`SQLiteStorage` реализует `ChatRepository` и `ConfigurationRepository`. Таблицы: conversations, messages, provider_configurations, application_settings; migrations фиксирует применённый последовательный префикс реального migration runner. Схема 2 хранит индексируемые метаданные сообщений рядом с JSON; recovery выбирает только status=generating через индекс, без десериализации всей истории. Сообщения упорядочены монотонным sequence, не timestamp. Используются prepared statements, foreign keys, WAL и транзакция для замены истории. JSON сообщений оставляет пространство для расширения MessagePart. Изменения схемы после v0.1 должны добавлять последовательные миграции; существующая версия не должна редактироваться задним числом.

Secrets лежат отдельно от БД. `EncryptedFileSecretStorage` использует AES-256-GCM с уникальным nonce и атомарной заменой файла. Это временное решение для локального пользователя, не OS vault. Модель угроз и правила переноса описаны в README. Настройки соединения и отдельный файл секретов не образуют общую транзакцию; при сбое диска возможен оставшийся неиспользуемый секрет. Сервер не отправляет ключи в ответы и не отображает upstream error bodies.

## HTTP API

| Метод и путь                              | Назначение                             |
| ----------------------------------------- | -------------------------------------- |
| GET `/api/health`                         | Проверка процесса                      |
| GET/POST `/api/conversations`             | Список / создание                      |
| GET/PATCH/DELETE `/api/conversations/:id` | История / заголовок / удаление         |
| POST `/api/conversations/:id/generate`    | NDJSON-поток message/delta/error/done  |
| POST `/api/conversations/:id/stop`        | Отмена                                 |
| GET `/api/models`                         | Модели включённых подключений          |
| GET/POST `/api/providers`                 | Публичные настройки / добавление       |
| PUT/DELETE `/api/providers/:id`           | Изменение / удаление                   |
| POST `/api/providers/:id/test`            | `/models`, обнаружение и сохранение    |
| GET/PUT `/api/settings`                   | Избранное и последняя выбранная модель |

Mutation-запросам нужен `X-Axiom-Client: chat`; JSON body. Проверяются Host и Origin; CORS не включён. Сервер слушает loopback, а локальные API-адреса провайдеров разрешены намеренно для LM Studio/Ollama. Этот режим не является безопасным публичным сервером. Markdown не разрешает raw HTML; данные провайдера не исполняются как код. Вложения ограничены по размеру и типам на API и UI.

## Проверки и основания выбора

Тесты Core не требуют браузера или сети. HTTP-тест адаптера использует временный локальный сервер и проверяет wire format, UTF-8, обрыв SSE и обработку ошибок. Браузерные тесты проверяют собранное приложение. Проверяются повторное открытие SQLite и реальный перезапуск дочернего API-процесса после принудительного завершения во время Mock streaming. UI проверяется перезагрузкой и повторным открытием диалога.

Официальные справочники: [Node 24 SQLite](https://nodejs.org/download/release/latest-v24.x/docs/api/sqlite.html), [Vite](https://vite.dev/guide/), [OpenAI Chat Completions](https://platform.openai.com/docs/api-reference/chat/create).

## Package boundaries

Каждый пакет компилируется TypeScript project references в `dist` с `module/moduleResolution: NodeNext`, JavaScript ESM, declarations и maps. Относительные импорты пакетов имеют `.js` extensions. Exports указывают только в `dist`, без development-ветки на src. Shared → core/providers/storage — порядок сборки, а зависимости трёх последних направлены только к shared. Серверный bundle оставляет workspace imports внешними; Vite получает скомпилированный shared. Тест запускает все пакеты в обычном Node с `--no-experimental-strip-types`.

## Последовательная запись settings

React обновляет локальное состояние немедленно; ref хранит последний снимок, а функциональные изменения не теряют соседние клики. SerializedWriter допускает ровно один PUT в полёте и объединяет промежуточные снимки. Более новый запрос начинается только после завершения предыдущего. Ошибка устаревшего снимка не блокирует новый; ошибка последнего отображается в UI, снимок остаётся для кнопки «Повторить». Promise rejection обрабатывается внутри writer. Результат начального GET не может затереть последующее пользовательское изменение.

Гарантия относится к одному экземпляру Chat и успешно доставленным записям. Нет распределённого revision-протокола между вкладками, offline outbox и гарантии доставки после закрытия страницы. При недоступном сервере интерфейс сообщает ошибку, а не обещает сохранение.

## Расширяемость без новых функций

ContextBuilder и TokenEstimator заменяются через constructor injection. Memory/summaries и tool orchestration не реализованы. Типы частей и единицы отбора контекста дают основу для их последующего внедрения. Таймеры и SSE остаются в Providers. SecretStorageRegistry позволяет composition root выбрать backend; AES-реализация не проникла в business logic. Подробности: CONTEXT.md, STORAGE.md, SECURITY.md и PROVIDERS.md.
