# SQLite и миграции — alpha.2

Реализации находятся только в `packages/storage`. Сервер создаёт SQLiteStorage, Core принимает ChatRepository. Один процесс владеет локальной БД; одновременные серверы на одном файле не поддерживаются (в частности, recovery предполагает, что прежний процесс остановлен).

## Schema 2

`conversations`, `provider_configurations`, `application_settings` сохраняют совместимый формат alpha.1. Таблица messages:

| Поле                   | Назначение                                                             |
| ---------------------- | ---------------------------------------------------------------------- |
| sequence               | AUTOINCREMENT, порядок сообщений                                       |
| id                     | Уникальный ID                                                          |
| conversation_id        | Foreign key с ON DELETE CASCADE                                        |
| role, status           | NOT NULL, допустимые значения ограничены CHECK                         |
| created_at, updated_at | Время создания и последней записи                                      |
| model_id, provider_id  | Необязательные идентификаторы                                          |
| data                   | Исходный Message JSON, включая MessagePart и дополнительные метаданные |

Индексы: `(conversation_id, sequence)` и `(status)`. JSON оставлен целиком, чтобы сохранить части и неизвестные расширения прежних сообщений. Repository синхронизирует колонки и JSON одной SQL-командой; recovery также обновляет оба представления. Смена conversationId/createdAt существующего message ID отклоняется. Внешние SQL-записи в обход repository не поддерживаются.

## Recovery

После успешной миграции выполняется индексированный UPDATE `WHERE status='generating'`: статус переводится в aborted, updated_at и соответствующие JSON-поля обновляются. История complete/error/aborted не читается и не десериализуется JavaScript-кодом. Тест проверяет использование messages_status через EXPLAIN QUERY PLAN и сохранность остальных строк.

## Migration runner

`runMigrations` получает упорядоченный список Migration {version, name, up}. Версии — последовательные уникальные числа от 1. Записанные версии должны быть точным префиксом плана. Неизвестная более новая схема, пропуск или дублирование приводят к отказу запуска.

Каждая неприменённая миграция выполняется в BEGIN IMMEDIATE / COMMIT. Запись версии входит в ту же транзакцию. Ошибка вызывает ROLLBACK, включая DDL и данные. Ранее успешно завершённые миграции остаются применёнными: после ошибки база находится на последней известной версии, не в промежуточном состоянии.

- Migration 1: зафиксированная исходная схема alpha.1. База alpha.1 уже содержит version=1, поэтому этот шаг пропускается.
- Migration 2: перенос messages в таблицу с индексируемыми колонками. Сохраняются ID, sequence, conversation, JSON, роли, статусы, время и ссылки на модель/провайдера. Затем старая таблица удаляется в этой же транзакции.

Если legacy JSON повреждён или не содержит обязательных полей, migration 2 откатывается. Повреждённые записи не выбрасываются ради успешного запуска. Нужно восстановить/исправить исходные данные; ошибка запуска указывает миграцию. При исключении конструктор закрывает соединение SQLite.

При следующих изменениях добавляйте migration 3 и далее, не редактируйте уже выпущенные миграции. Rollback означает атомарный откат неудачного шага, не автоматический downgrade приложения. Для возврата к alpha.1 нужна соответствующая резервная копия.

## Проверки

Тесты: пустая БД, независимая fixture старой схемы с вложениями/config/settings, повторный запуск, искусственная ошибка DDL и повторная успешная попытка, повреждённый JSON без потери исходной таблицы, неизвестные версии, foreign-key cascade и recovery. Отдельный процессный тест завершает API во время streaming и открывает ту же БД новым процессом: сохранённая часть ответа восстанавливается как aborted.

Перед обновлением рабочей БД остановите старый сервер и сделайте backup. Для текущей рабочей папки перед alpha.2 создана согласованная SQLite backup в `.axiom/backups/`; она не содержит файлов секретов. Копирование одного основного SQLite-файла во время работы с WAL не заменяет корректную резервную копию.
