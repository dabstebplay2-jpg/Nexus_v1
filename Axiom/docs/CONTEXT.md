# Context policy — alpha.2

Реализация: `packages/core/src/context.ts`. `ContextBuilder.build` принимает Conversation, readonly Messages и Model, возвращает выбранные сообщения, estimatedTokens, inputBudget и droppedMessageIds. ChatCore получает builder через конструктор. Ни provider SDK, ни tokenizer поставщика, ни SQLite здесь нет.

## Правило включения

`includeInModelHistory` — отдельная тестируемая policy:

- complete участвует как обычное сообщение;
- aborted assistant участвует, если есть непустой текст, файл или изображение;
- пустой/пробельный aborted assistant не участвует;
- error и generating исключаются;
- незавершённые tool-call/reasoning metadata сами по себе не считаются готовым частичным ответом.

В сценарии «длинный ответ → Stop → продолжи» непустой частичный ответ находится между исходным вопросом и новым пользовательским сообщением. Метаданные status не пересылаются OpenAI API; отправляется обычное assistant content. Ошибка провайдера не становится нормальным ответом. Политика не меняет и не удаляет записи в БД.

## Бюджет

Default RecentTurnsContextBuilder:

```text
window = model.contextWindow, иначе 8192
reserve = min(2048, floor(window / 4))
inputBudget = floor(window × 0.9) − reserve
```

10% — запас на погрешность и служебные токены, reserve — место для ответа. Это бюджет входа, а не параметр max_tokens поставщика. Недопустимый размер окна отклоняется. Значения fallbackContextWindow, outputReserve и safetyRatio можно изменить в ContextPolicy при создании builder.

ApproximateTokenEstimator оценивает UTF-8 bytes/3 с округлением вверх, добавляет 8 токенов на сообщение. Содержимое файлов и их имена учитываются, на изображение выделяется фиксированная оценка 4096 токенов. Tool payload и reasoning summary/metadata оцениваются через сериализованное содержимое. Это детерминированная эвристика с запасом, но не верхняя граница реального tokenizer; особенно неточны vision и бинарные/кодовые представления. Можно внедрить другой TokenEstimator, не меняя ChatCore.

## Отбор

Все complete system-сообщения закрепляются в начале запроса, в исходном взаимном порядке. Остальные сообщения группируются в ходы: user и последующие assistant/tool до следующего user. Одиночные assistant/tool без предшествующего user исключаются. Из конца выбирается непрерывный суффикс целых ходов. При первом не поместившемся старом ходе отбор останавливается; более старые короткие фрагменты не вставляются вместо него.

Части сообщений не режутся, tool-call/result внутри хода не разделяются бюджетом. Полный валидатор/исполнитель tool chains ещё не реализован. Если system или самый новый ход сами не помещаются, выбрасывается ContextBudgetError с предложением сократить сообщение/вложения или сменить модель. Последний запрос не теряется молча. Vision capability проверяется только для реально выбранного контекста.

ChatCore строит предполагаемую историю **до** транзакции edit/regenerate. Поэтому ошибка бюджета не удаляет старые сообщения. Ограничение влияет на payload запроса, а не на отображаемую историю или её хранение.

## Границы alpha.2

Нет summary, RAG, memory, автоматического извлечения вложений, UI-индикатора token budget и отдельного system prompt editor. Builder/estimator — точки расширения для этих будущих данных. Сейчас история одного диалога всё ещё читается из repository полностью перед отбором; ограничен объём запроса модели, но не память для чтения очень длинного диалога. Пагинация и запрос хвоста по бюджету требуют последующего расширения repository.
