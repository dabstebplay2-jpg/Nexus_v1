# Secret Storage и модель угроз — alpha.2

## Архитектурная граница

`SecretStorage` остаётся портом в shared. Core не знает, каким способом хранятся ключи; адаптер провайдера получает секрет через этот порт. Реализация AES и файловые операции остаются в Storage.

Composition root выбирает backend через SecretStorageRegistry. По умолчанию зарегистрирован только `encrypted-file`; его можно явно выбрать `AXIOM_SECRET_BACKEND=encrypted-file`. Неизвестное имя завершает запуск с понятной ошибкой. Автоматического перехода с недоступного защищённого backend на файловый нет.

Будущий Windows backend может зарегистрироваться отдельной фабрикой и реализовать тот же интерфейс для Credential Manager/DPAPI. В alpha.2 он **не реализован**: запуск PowerShell с API-ключом или самодельная криптография не добавлены ради формальной поддержки Windows. Потребуются отдельные проверки OS account scope, упаковки, ошибок и переноса ключей. Выбор backend не означает автоматическую миграцию секретов между ним и AES-файлом.

## Что делает текущий backend

AES-256-GCM использует случайный nonce и authentication tag, master.key создаётся из cryptographic random bytes. Секреты записываются во временный файл и заменяют secrets.json. Ключи не хранятся в application settings/SQLite/localStorage, не возвращаются в GET API и не печатаются в логи. Пустой API Key при редактировании сохраняет прежний ключ, отдельный флаг удаляет его.

## От чего это не защищает

master.key лежит рядом с secrets.json. Доступ к обоим позволяет расшифровать ключи. Это не защита от malware, администратора, компрометации текущего профиля или копии всей папки данных. API-ключ кратковременно существует в памяти браузера при вводе и в памяти процесса сервера при использовании; гарантированного стирания managed string нет. История/вложения SQLite не зашифрованы. На Windows mode 0600 не заменяет ACL. Секреты и конфигурации в разных файлах не имеют общей транзакции; при сбое записи возможен неиспользуемый секрет.

Локальный API не имеет пользовательской авторизации: он рассчитан на один доверенный профиль и loopback. Проверки Host/Origin и заголовка клиента уменьшают риск вызовов из чужой веб-страницы, но не останавливают другой локальный процесс. Base URL может указывать на локальный сервер намеренно; это не публичный защищённый прокси. Удалённый HTTP-провайдер без TLS не защищает ключ и контент в сети — используйте HTTPS для удалённых endpoints.

## Эксплуатация

Держите `.axiom` в личном каталоге с ограниченным доступом. Не включайте master.key, secrets.json или SQLite в Git/архивы исходников. Backup секретов должен включать ключ шифрования и храниться с соответствующей защитой. Потеря master.key при существующем secrets.json вызывает отказ, а не генерацию нового ключа поверх старого хранилища. Для выпуска на несколько пользователей или в сеть нужны отдельные auth, OS vault и политики доступа.
